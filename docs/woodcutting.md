# Resident gathering

An unassigned resident with Auto enabled looks for a revealed, reachable tree or rock deposit within five map units. Construction, roadwork, an assigned workplace and urgent needs keep their existing priority. Each resource cell has one active worker; an interrupted worker releases the claim. A built camp, storehouse or market must be reachable, and the relevant storage must have room.

Trees and rock deposits can be selected directly. Attack (`A`) and Work (`W`) on a resource start harvesting. New Move and Attack commands immediately replace the current harvest, including its claim. Move reaches the requested destination before any automatic fighting, harvesting or delivery; Attack on the ground advances while fighting nearby enemies. A right click (and Work on the ground) means go there and take up the work about it: a building site or damaged building within four paces first, then a road wanting work, then the nearest tree or rock; with none, the unit simply goes. A right click on a house, tent or the camp sends the unit in to rest. A building is picked by its drawing as well as its footprint, the frontmost first, so clicking its walls or roof picks it out. Keyboard orders work whatever mode an input method is in: the game keeps text input off unless an editor or a text field takes typing, since an input method composing Korean, Japanese or Chinese swallows the letter keys. Stop (`S`) releases work claims and clears the order while retaining cargo. Auto (`T`) replaces the former duty modes. Auto-off units wait between orders; residents no longer sleep because of the time of day.

Free Auto residents stroll along reachable routes around home or camp and scan for work while walking. A player order suspends that search until its destination is reached. Resource work shares navigation, exclusive claims, capacity checks and delivery for wood and stone. Mining swings a pickaxe for six seconds, removes the visible boulder, collects three stone, and carries it to storage. Quarriers use the same mining flow rather than producing stone without visiting a deposit. Depleted boulders are recorded in map format 4; formats 1–3 remain readable.

Building and road plans do not instantly clear trees or award wood. A worker clears blocking trees before construction can pass them, delivers the logs while the store has room, and returns to the site. The first camp or store can retain logs while its own foundation is cleared, then accept delivery once complete. A road joined to an unfinished plan first advances its connected parent to the junction. A road crossing a junction grows from that junction; the worker walks back before building the other side. A site beside a road that is still only planned waits for it: its builder first lays that road, or the stretch of its chain that can be laid now, until a laid road reaches the site, then raises it. A site already begun keeps going, and one whose road cannot be reached is built anyway.

A thin bottom-center handle expands into Build only when nothing is selected. Categories, building choices, resource/building details and unit information share one retained surface: its size morphs around the center as the content crossfades. Menus fit their button count, and selection switches suppress the global hover handle. UI time keeps transitions moving while simulation is paused; browser reduced-motion preferences and the native `HEARTHOLD_REDUCED_MOTION=1` override skip them. It queues explicit global construction requests and assigns an idle resident, including one with Auto off. When nobody is idle, the request just clicked takes the nearest resident off automatic work (gathering, hauling, a workplace or another site), who drops it and goes at once; meals, rest, prayer, fights, expeditions and departures keep their people, and requests still waiting later take only idle residents. It preserves direct orders already in progress. A stopped resident is excluded from earlier queued requests until Auto is enabled or a new request arrives. The unit Build button morphs the same surface into building choices for the selected crew; selecting another unit returns it to that unit's information.

Hunger, cold, fatigue and other conditions are independent tags rather than alternative actions. Auto switches to an available meal or rest before resuming an order, using the same decision path during ongoing work. Construction clearance never waits on storage: with the wood store full or out of reach, the builder fells the tree anyway and leaves its logs by the work (the user saw roads stall for good when it waited). Manual units retain their condition tags without automatic needs interruptions.

Hostels, inns and grand inns provide guest accommodation only. Residents use their assigned homes for rest and never enter guest lodging for meals or sleep. Old resident lodging orders are canceled, existing resident occupants leave through the door without changing their Auto setting, and guests who settle release their beds and leave the lodging. Lodging inspectors list Guests; home inspectors list Residents.

The resident walks to the actual rendered tree position and chops for six simulation seconds. The axe winds up and strikes every 0.7 seconds, and each strike is heard: from any woodcutter at work near the middle of the view, and louder from a selected one. The tree then falls over 0.8 seconds while the worker collects it. The worker carries a visible bundle of three logs to storage. Stock increases only on arrival; any overflow stays on the carrier for a later delivery. Lumberyard workers use the same cutting and delivery path.

The axe, tree fall and collection progress use simulation time. Tree effects reuse the existing tree painter and depth rows. Recent work events are bounded, old sounds are discarded, and effects pass through the existing EffectManager. Edit mode does not advance the simulation; Pause and Stop retain their existing playback behavior.

## Verification

`tests/game/testWoodcutting.cpp` covers approach, harvesting and delayed deposit; range, base and capacity requirements; exclusive claims and interruption; overflow preservation; and strike timing. `testMining.cpp` covers physical stone extraction, delivery, exclusive claims, interruptions, storage capacity and saved depletion. `testUnitOrders.cpp`, `testCommandUi.cpp`, `testConstructionClearing.cpp` and `testRoadConstruction.cpp` exercise manual orders, task assignment, actual clearance and connected construction; `testConstructionOrders.cpp` covers laying a site's road before raising it and a clicked request taking a resident off automatic work; `testPlayerInput.cpp` covers right clicks on open ground, homes and building drawings, and letter keys reaching the game past an input method. `testSpeechAudio.cpp` verifies that axe and pickaxe hits release their audio slots before another stroke and stay silent while stopped.

Native validation uses `SDL_AUDIODRIVER=dummy`. Browser validation uses an isolated, muted browser. Both the game and GameEngine use the same production game libraries.

The optional resident profiler supports a deterministic woodcutting scenario:

```sh
meson compile -C build-web Hearthold-residents-profile
HEARTHOLD_PROFILE_WORKERS=5 HEARTHOLD_PROFILE_WOODCUTTING=1 \
  node tools/profile_browser_gameplay.mjs build-web/web woodcutting.json \
  Hearthold-residents-profile.html
```

Package the optional profiler's `.js`, `.wasm`, `.data` and HTML shell in the web directory before running that command. The standard web package contains only the game and GameEngine. The browser check captures approach, axe windup and strike, tree fall, carrying and storage; it asserts stock stays at 80 until delivery, then becomes 83. Validation uses an isolated, muted browser and closes its own processes.

Use `HEARTHOLD_PROFILE_MINING=1` instead of `HEARTHOLD_PROFILE_WOODCUTTING=1` for the same check with a pickaxe, a finite boulder and three stone delivered to camp.
